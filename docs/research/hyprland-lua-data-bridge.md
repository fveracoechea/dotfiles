# Hyprland Lua data bridge: how Nix data reaches hand-written Hyprland Lua

Research date: 2026-09-12. Hyprland version researched: 0.55.4 (tag `v0.55.4-b`, commit `a0136d8`, the version held in this repo). Home Manager module: current nixpkgs `wayland.windowManager.hyprland` with the 0.55 Lua backend (`configType` default flips to `"lua"` at `home.stateVersion` 26.05).

The decision this research serves: the human chose hand-written Hyprland Lua in the Config Directory (ADR-0005 pattern), forbids Nix-generated Lua source, and suggested Nix-generated JSON or YAML for host data (monitors, Theme values, paths) that the Lua config reads. This document studies what the embedded Lua of Hyprland 0.55 gives us, whether a JSON or YAML parser exists without adding a runtime dependency, whether pure-Lua parser vendoring is sound, and which data bridge format to use.

## TL;DR verdict

Use JSON. One Nix-generated data file, read by hand-written Lua through one vendored pure-Lua parser.

- `$XDG_CONFIG_HOME/dotfiles/hyprland.json`, generated by Home Manager with `xdg.configFile."dotfiles/hyprland.json".text = builtins.toJSON { ... }`. This is generated data, not generated Lua, so it honors the constraint. The separate target avoids overlapping the out-of-store `hypr` directory with a second Home Manager file. It also matches the ADR-0005 carve-out that keeps small generated data files (karabiner, sunshine `apps.json`) as Nix-generated.
- `config/hypr/lib/json.lua`, a vendored copy of `rxi/json.lua` (MIT, 369 lines, pure Lua, no `os` or `io` calls). Hyprland embeds Lua 5.4 with the full standard library and no JSON parser, so a vendored parser is the only zero-runtime-dependency option. I tested the parser on Lua 5.4.7 with a monitor list, Theme colors, and a browser path: it decodes all of them correctly.
- A small hand-written `config/hypr/bridge.lua` module finds the data file from `XDG_CONFIG_HOME`, with `$HOME/.config` as the fallback. It wraps the read with `pcall`, so a missing or malformed file degrades to defaults and shows an error, instead of killing the config.
- The generated data file is not watched by Hyprland's config watcher (only `require`-loaded files are), so Home Manager activation should wire `onChange` to `hyprctl reload config-only`.

YAML loses on every axis: no parser exists in the embedded runtime, and every pure-Lua YAML implementation is large or incomplete. Environment variables and ad-hoc line formats lose on typing, editor tooling, and validation.

## 1. The embedded Lua environment of Hyprland 0.55

All claims in this section come from `src/config/lua/ConfigManager.cpp` at tag `v0.55.4-b`, verified against the live wiki.

- Interpreter: Lua 5.4 (not LuaJIT). `reinitLuaState()` calls `luaL_newstate()` and `luaL_openlibs()`, so the full standard library is present: `io`, `os`, `string`, `table`, `math`, `coroutine`, `debug`, `utf8`, `package`.
- The `debug` library is partly disabled: `debug.sethook` and `debug.gethook` are removed, because Hyprland runs a watchdog hook (`guardedPCall`) that kills scripts which run past a timeout (`LUA_TIMEOUT_CONFIG_RELOAD_MS` for reloads, separate timeouts for keybind callbacks and `hyprctl eval`).
- `package.path` is overwritten, not extended, on every state init: `package.path = "<dir of hyprland.lua>/?.lua;<dir of hyprland.lua>/?/init.lua"`. So `require("lib/json")` resolves to `<configdir>/lib/json.lua`. Modules must live in the Config Directory tree, or the config must prepend paths itself.
- `package.cpath` is left at the Lua default. C modules are loadable. A restriction to Lua-only modules (PR #14526) shipped in 0.55.1 and was reverted (PR #14533) after packager and user backlash; the maintainer still wants C modules blocked eventually, so C-module loading is a shaky foundation and best avoided.
- `require` is wrapped (`safeLuaRequire`): the original is kept as `__require`. A runtime error in a required file is reported to the config error overlay and the module returns an empty table, so one broken file does not stop the rest. A module that does not exist still throws a real error, catchable with `pcall`. The wiki documents both behaviors.
- `package.searchers[2]` is hooked so every file that `require` resolves is tracked. The config watcher watches tracked files with inotify and reloads the whole config when any of them changes.
- Reload re-creates the Lua state from scratch (`reinitLuaState()` in `reload()`), clears `package.loaded` for everything except the standard library, then runs a two-phase load: syntax check first, then full execution. A syntax error keeps the old config alive. If no keybinds registered after a failed load, emergency binds activate (SUPER+Q, SUPER+R, SUPER+M).
- Config selection: `hyprland.lua` wins over `hyprland.conf` at startup, checked once (news post "Lua-ification of Hyprland configs"). Hyprlang is deprecated; new features land in Lua only.
- Validation: `hyprland --verify-config` starts no compositor and prints config errors (`src/main.cpp`). `hyprctl eval` runs Lua in the live compositor state (Lua backend only; the live compositor on this machine still runs hyprlang, so `hyprctl eval` currently answers "eval is only supported with the lua config manager"). `hyprctl` also has a built-in Lua REPL.
- Editor tooling: Hyprland generates LuaLS stubs at build time and installs them under `/usr/share/hypr/stubs/`. Verified on this system: `/run/current-system/sw/share/hypr/stubs/hl.meta.lua` exists. The Home Manager module also writes `hypr/.luarc.json` pointing at `${finalPackage}/share/hypr/stubs` when `configType == "lua"`.

What this means for the bridge: a hand-written config tree under `~/.config/hypr/` can `require` helper modules from the same directory, can read any file with `io.open`, can query the environment with `os.getenv`, and gets file-watching for free only for `require`-loaded Lua files. There is no bundled JSON or YAML parser: I searched `src/config/lua/` and the whole repo for `json` and `cjson` bindings and found none, and the Lua 5.4 standard library has none.

## 2. Is vendoring a pure-Lua JSON parser sound?

Yes, with one file and a clear license.

- Candidate: `rxi/json.lua` (github.com/rxi/json.lua, version 0.1.2). 369 lines, MIT license, no dependencies, pure Lua, works on Lua 5.1 through 5.4.
- The decoder is strict: it errors on trailing garbage, invalid escapes, control characters, and bad literals, with line and column in the message. It runs no code: no `load`, no `os`, no `io`. This matters because the parser executes inside the compositor process.
- Verified by test on this machine: `nix shell nixpkgs#lua5_4` gives Lua 5.4.7, the same interpreter major.minor as Hyprland 0.55.4 embeds. `json.decode` on a file shaped like the proposed bridge (`monitors` list with the real DP-1 spec string from `config.dotfiles.hyprland.monitors`, a `theme` table with three `rgb(...)` strings, and a `browser` path) returned every value correctly.
- The file must live under the config directory because Hyprland overwrites `package.path` to that directory only. `config/hypr/lib/json.lua` with `require("lib/json")` fits.
- Maintenance cost is near zero: JSON is frozen (RFC 8259), the parser is finished software, and a future swap for a C module (`cjson` through `luaPackages`) would need a runtime dependency plus the shaky `package.cpath` surface, so vendoring is also the more robust long-term choice.

Rejected parser alternatives: `lunajson` (equally viable, slightly larger), `serpent` (serializes Lua, not JSON), `lyaml` (C library, libyaml dependency, needs `luaPackages` and `package.cpath`, so it violates the no-runtime-dependency constraint).

## 3. YAML is not a candidate

- No YAML parser ships with Hyprland or with Lua 5.4.
- Pure-Lua YAML implementations are either incomplete subsets or abandoned. The maintained implementations (`lyaml`) bind libyaml, a C library, so they need `luaPackages` plus `package.cpath`: a runtime dependency and a surface the Hyprland maintainer wants to close (PR #14533 discussion).
- The bridge data is flat: a list of monitor strings, a Theme color table, and a few paths. YAML's nesting, anchors, and multi-line scalars buy nothing here. Rejected.

## 4. Format comparison

| Axis | JSON + vendored parser | YAML | Environment variables | Line format (`key = value`) | Nix-generated Lua data module |
|---|---|---|---|---|---|
| Parser burden | One 369-line vendored, license-clear, tested parser | None exists without a C runtime dependency | None (`os.getenv`) | Hand-written parser, hand-tested, hand-maintained | None |
| Typing | Full: strings, numbers, booleans, arrays, objects, `null` | Full in theory; unusable here | Strings only; lists need ad-hoc encoding | Strings only | Full Lua values |
| Generation | `builtins.toJSON`, one line of Nix | Needs a Nix YAML emitter (none in the stdlib; `pkgs.formats` covers JSON and TOML, YAML only via conversion) | String building, per-variable | String building | `lib.generators.toLua` |
| Validation | `jq` or `nix flake check` can parse the generated file; parse errors surface in the config error overlay with line and column | Same as JSON where a parser exists | Invisible; a missing var is a silent `nil` | Only by running the config | Eval-time type checks via the Nix option system |
| Editor tooling | Treesitter, formatters, JSON schema possible | Treesitter | None | None | None (generated) |
| Reload behavior | Data file is not watched; needs `onChange` reload or manual `hyprctl reload` | Same | Not watched at all | Same | Watched by inotify and auto-reloaded, because `require`-loaded files are tracked |
| Home Manager fit | Native (`xdg.configFile.text`, the ADR-0005 generated-data pattern); the generated target must stay outside the out-of-store `hypr` tree | Awkward | `home.sessionVariables` pollutes the process environment with config data | Native but bespoke | Forbidden by the human's constraint |
| Security | Parser runs no code | Same | Lowest: env is read-only data | Parser is hand-written code in the compositor | Generated Lua is reviewable but collapses the Lua/Nix seam the human wants kept |
| Failure mode | `pcall` around decode, error overlay shows the message | Unusable | Silent `nil` defaults | Parser bugs corrupt values silently | Eval errors |

Notes on Hyprland-native data APIs, examined and rejected as bridges:

- `hyprctl -j <command>` outputs compositor state as JSON. It is an output channel, not an input channel: it cannot carry host monitor intents into the config at parse time.
- `hl.env(name, value, dbus?)` sets an environment variable in the compositor process during config parse (`src/config/lua/bindings/LuaBindingsConfigRules.cpp`). It is an output of the config, not an input from Nix. Feeding data through environment variables would instead rely on `home.sessionVariables` and the session launch path, with parse-time visibility that depends on how Hyprland starts. Too fragile for this seam.
- `hyprctl eval` runs Lua in the live state. Useful for debugging the bridge once the Lua backend is active, not a config-input channel.
- `hipe.hypr` (third-party plugin manager) shows the ecosystem pattern: extend `package.path` from Lua, then `require`. Our bridge uses the same mechanism with no network installs.

## 5. Home Manager integration shape

Current module behavior (nixpkgs `hyprland` HM module):

- With `configType = "lua"`, the module generates `hypr/hyprland.lua` whenever `systemd.enable || settings != {} || extraLuaFiles != {} || plugins != [] || extraConfig != ""`. Since `systemd.enable` defaults to true, some generated Lua always appears while the module owns the file. Generated Lua is forbidden here, so the human's choice means the module must stop owning `hyprland.lua`.
- `extraLuaFiles` copies hand-written files from the repo into `~/.config/hypr/` as store-backed Home Manager files, and the generated `hyprland.lua` gains a `package.path` extension plus `require` calls. Edits need a rebuild (no out-of-store live editing), and the module asserts it owns `hyprland.lua`. This fits the constraint's letter (the required files are hand-written) but breaks the ADR-0005 live-edit property and still ships Nix-generated bootstrap Lua.
- The ADR-0005 pattern instead symlinks the whole `config/hypr/` directory out of store: `xdg.configFile."hypr".source = config.lib.file.mkOutOfStoreSymlink "${repo}/config/hypr"`. Then hand-written `hyprland.lua`, `bridge.lua`, and `lib/json.lua` are live-edited. The generated JSON must use a target outside `hypr`, such as `dotfiles/hyprland.json`. Home Manager rejects a managed child file under a non-recursive directory symlink because writing it would modify the source directory.

One ownership collision to resolve at implementation time: the HM module writes `hypr/.luarc.json` and (with systemd enabled) `hypr/hyprland.lua` as separate `xdg.configFile` entries. A whole-directory out-of-store symlink and those per-file entries target the same paths and conflict. A generated `hypr/data.json` would have the same problem. The options are to drop the HM hyprland module's file outputs and hand-write the systemd startup hook (`hl.on("hyprland.start", ...)` with the `dbus-update-activation-environment` command), or recursively link each file from the out-of-store source tree so Home Manager can also own child targets. The first option keeps live discovery of new files and is simpler. The repo already sets `package = null` and `portalPackage = null` and takes Hyprland from the NixOS module, so the package-coupling cost of a decision here is low.

Data file reload: the config watcher tracks only `require`-loaded files. The generated JSON changes on HM switch, so wire `onChange = reloadConfig` on its `xdg.configFile` entry, where `reloadConfig` is the module's existing multi-instance `hyprctl -i <instance> reload config-only` snippet. Without that, a Theme or monitor change needs a manual reload after switch.

## 6. Recommended seam

One narrow seam, one file, one schema:

1. `$XDG_CONFIG_HOME/dotfiles/hyprland.json`, Nix-generated:
   - `monitors`: the host's `config.dotfiles.hyprland.monitors` list, verbatim strings.
   - `theme`: the palette colors Hyprland needs, already in `rgb(...)` form (the `toRgb` helper from the current `theme.nix` moves into the generating module).
   - `paths`: string paths such as the browser.
   Placement: `xdg.configFile."dotfiles/hyprland.json".text = builtins.toJSON { ... }` with `onChange` wired to the reload snippet. This target does not overlap the out-of-store `hypr` tree.
2. `config/hypr/lib/json.lua`: vendored `rxi/json.lua`, MIT header kept.
3. `config/hypr/bridge.lua`, hand-written: build the data path from `XDG_CONFIG_HOME` or `$HOME/.config`, open it with `io.open`, run `json.decode` inside `pcall`, validate the shape, and return one table with defaults on failure.
4. Hand-written `config/hypr/hyprland.lua` (plus the existing split: `monitors.lua`, `bindings.lua`, `windowrules.lua`, `theme.lua`): `require` the bridge and feed `hl.monitor`, `hl.config` border colors, and `hl.env` from the returned table.

Why JSON over the alternatives: the parser is the only audited, tested, frozen piece of code in the seam; the Nix side is one `builtins.toJSON`; typing is exact for every value the bridge carries; `jq` can validate the generated file in a flake check; and the data file stays out of the hand-written Lua the human wants to own.

## Remaining human choices

1. Ownership of `~/.config/hypr`: whole-directory out-of-store symlink (recommended, preserves ADR-0005 live editing) versus HM `extraLuaFiles` (rebuild per edit, keeps the module's systemd hook generation but ships a Nix-generated bootstrap `hyprland.lua`).
2. If the whole directory is symlinked: how to replace the module's systemd integration (hand-written `hl.on("hyprland.start")` hook recommended) and where `.luarc.json` lives (hand-written or generated into the repo's `config/hypr/`).
3. Exact generated JSON schema and target, and which palette keys the Theme section carries (the current Hyprland theme uses `blue`, `flamingo`, `surface2`).
4. Reload wiring: `onChange` reload snippet on the generated JSON (recommended) or manual `hyprctl reload` after switch.
5. Optional tooling: a flake check that runs the generated JSON through `jq`, a `hyprland --verify-config` check (costs a Hyprland build in the check), and `luacheck` or `stylua` for `config/hypr/`.
