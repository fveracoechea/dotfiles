# Split nixpkgs channels by package owner

This flake pulls from two nixpkgs channels. Package ownership decides the channel by default. The **Release Channel** builds packages owned by the System layer on both hosts. The **Latest Channel** (`nixpkgs-latest`, `nixpkgs-unstable`) builds packages owned by the Home layer. This policy applies to Nix packages and Nix flake inputs; Homebrew and Volta have separate update policies. Before this, one `nixos-unstable` input fed everything, so a `nix flake update` to get a newer coding agent also moved the kernel and forced a Hyprland source build.

Package ownership decides the channel, with three narrow departures:

- **Version-Coupled Package.** A package follows its partner's channel when compatibility depends on a shared protocol, ABI, IPC interface, patch process, or configuration format. The Hyprland satellites (`xdg-desktop-portal-hyprland`, `quickshell`, `hyprpaper`, `hyprshot`, `hyprpicker`, `hyprcursor`, `hypridle`, `hyprlock`) therefore come from the Release Channel with the compositor. Ultrashell keeps its own current source revision but builds its Hyprland dependencies from the Release Channel. Compatibility takes priority over freshness, and each coupled set must be explicit.
- **Packaging Exception.** Spotify sits in the darwin System layer only because nix-darwin links `Spotify.app` from `environment.systemPackages` into `/Applications/Nix Apps` for Spotlight and Launchpad. It is an app, so it takes the Latest Channel, and `spicetify-cli` takes the same channel because it patches the Spotify build. Use this exception only when Home Manager cannot practically own the package while the System owns its required integration.
- **Channel Hold.** A Home-owned package may temporarily come from the Release Channel when its Latest Channel package does not build or work. The use site records the failure and the condition for returning to the package owner's channel.

## Consequences

- Routine updates advance only `nixpkgs-latest`. Home Manager and app or tool inputs update separately when needed. Release updates move `nixpkgs-stable`, `nixpkgs-stable-darwin`, and nix-darwin together. This preserves the main isolation goal: updating Home apps and development tools must not move the kernel, services, login path, compositor, or other System components.
- The System Toolset contains only packages needed for boot, administration, recovery, or by a System Module. `vim`, `git`, and `curl` form the general recovery set; `ethtool` remains for network administration. Personal development tools and desktop utilities belong to Home Manager. Duplicate commands remain only when the System copy has a clear recovery purpose.
- System Modules keep integrated packages such as Docker and login shells on the Release Channel. Home Manager owns companion tools such as `lazydocker`, `docker-compose`, `pavucontrol`, `nautilus`, `wl-clipboard`, and `libnotify`, so they use the Latest Channel. Firefox remains on the Release Channel while the NixOS `programs.firefox` option owns it.
- Gaming packages take the Latest Channel even where a System Module installs them: Steam, protontricks, `proton-ge-bin`, gamescope (which also serves the Steam Session), `gamescope-wsi`, LACT, OpenRGB, and Sunshine are routed through their module package options. GameMode stays on the Release Channel because the 26.05 module exposes no package option.
- On Linux, Handy comes from `pkgs.handy` in the Latest Channel and is owned by Home Manager. Its separate flake input and NixOS module are unnecessary. The System enables its standard uinput support, and the user belongs to both the `input` and `uinput` groups for global shortcuts and text injection. On macOS, the Homebrew cask remains because it provides native application registration; the duplicate Nix package is removed from the Home.
- `nixpkgs.pkgs` receives an already-built instance, and NixOS asserts that `nixpkgs.config` is empty in that case. So `allowUnfree` and `permittedInsecurePackages` live in `nixpkgsConfig` in `flake.nix`, shared by both instances, and hosts can no longer declare them.
- Home Manager runs on the Latest Channel through a plain `_module.args.pkgs` definition, which replaces the `mkDefault` that `useGlobalPkgs = true` supplies. Both module trees still evaluate Home Manager with the Release Channel's `lib`, so `home.enableNixpkgsReleaseCheck` is off on both hosts. Home Manager and `pkgs` do agree; only `lib` differs, and it supplies pure helpers. A Home Manager release that needs a newer `lib` function would break evaluation with a clear error.
- The Release Channel has one branch per platform: `nixos-YY.MM` for Linux in `nixpkgs-stable`, and `nixpkgs-YY.MM-darwin` for macOS in `nixpkgs-stable-darwin`. `stableSourceFor` picks by system, so call sites stay one line. nix-darwin asserts that its own branch corresponds to the Nixpkgs branch it evaluates against, so `nix-darwin` is pinned to `nix-darwin-YY.MM` and follows the darwin release branch. Bumping the release means moving all three refs together.
- The Latest Channel tracks `nixpkgs-unstable`, not `nixos-unstable`. `nixos-unstable` is gated on the NixOS VM integration tests as well as the nixpkgs jobset, so it trails by hours to a couple of days. That gating bought something when this input built the NixOS system; now the System layer comes from the Release Channel and this input builds only Home layers, which those tests do not cover. It is also the branch nix-darwin and standalone Home Manager recommend. `nixos-unstable-small` is fresher still but runs a reduced test set and builds fewer packages, so cache coverage is thinner.
- Home Manager follows `nixpkgs-latest` but its source revision updates separately. App and tool inputs also follow `nixpkgs-latest` and update individually. musnix and the Hyprland dependencies of Ultrashell follow `nixpkgs-stable`; nix-darwin follows `nixpkgs-stable-darwin`. There is no `hyprland` flake input: the compositor is a system package like any other and comes from the Release Channel, so it is always a `cache.nixos.org` hit rather than a source build against an overridden nixpkgs. The cost is that its version is the release's. 26.05 holds 0.55.4, the last version that reads `hyprland.conf`; 0.56 dropped hyprlang for `hyprland.lua`. The config must be ported to lua before the release moves to 26.11, and `wayland.windowManager.hyprland.configType` is set explicitly so the two can never drift apart.
- On NixOS, Zsh is a Version-Coupled Package because the System registers it as the login shell. Home Manager and tmux use `pkgs-stable.zsh` so the configured shell and the executed shell match. macOS keeps its native login shell, so its Home Zsh uses the Latest Channel. Shell tools and plugins remain on the Latest Channel.
- Unused flake inputs are removed rather than kept current. `neovim-config` is removed because no host or module consumes it.
- Spotify on macOS is fetched from a `web.archive.org` snapshot on both channels, because Spotify's own CDN serves only the current release. Wayback rate-limits with HTTP 429, so a Spotify version not already in the store can fail to fetch for a while. That is upstream packaging, not a consequence of this split, but it is the first thing to check when a darwin build fails on `SpotifyARM64.dmg`.
- Custom Packages and flake-input wrappers are built on the Latest Channel in `packages/default.nix`; consumers keep reading `dotfilesPkgs.<name>` and no call site knows the plumbing. System-only packages such as the compositor stay out of it and come straight from the System layer's Release Channel `pkgs`.
- Home modules receive `pkgs-stable` only for an explicit Version-Coupled Package or Channel Hold. Each use states its reason beside the assignment. Ordinary Home packages use the default Latest Channel `pkgs`; ordinary nixpkgs packages do not enter Dotfiles Pkgs.
- Latest Channel updates run `nix flake check`, `nixos-rebuild test --flake .#nixos-desktop`, and `darwin-rebuild check --flake .#macbook-pro` on applicable hosts. A Release update runs the same checks, stages the NixOS generation with `nixos-rebuild boot`, reboots, and validates boot, login, Hyprland, networking, audio, and the Steam Session before merge. After each Latest update, Zettlr is tested from the Latest Channel and its hold remains until both its build and launch succeed.
